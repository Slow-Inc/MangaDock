## Implemented behavior

- Account settings offer an explicit opt-in, permission-denied guidance, opt-out and a local test notification. No permission prompt on launch, login or foreground refresh. The existing native design tokens, 48dp actions and accessible status/error labels are reused.
- `expo-notifications` obtains an **Expo Push token**, using the existing EAS project ID, as required by Roadmap.md. Android transport is FCM. No server key or send API is embedded in Mobile.
- Authenticated, idempotent device registration; foreground and native-token-change refresh. The UI reports enabled only after an explicit server acknowledgement.
- Per-account opt-in and a persistent registration-owner marker. Owner changes cancel stale work. Explicit logout attempts server removal and native-token invalidation before disposing the accepted session; external session loss also queues cleanup. Native cleanup dismisses delivered notifications.
- Cold-start, background and foreground notification taps share the existing native destination parser. Only versioned, recipient-matching payloads reach supported product screens. Startup/listener duplicates are ignored. A cold notification may wait for login; signing into a different account discards it. Reader entitlements and staff/Studio gates remain in their existing screens.
- Optional push failures do not hold up product startup. Token acquisition, HTTP requests and native cleanup have bounded waits. If both server and native cleanup fail, logout still proceeds and the persisted owner marker allows a later retry. This is not a guarantee of remote revocation while offline.
- `EXPO_PUBLIC_PUSH_ENABLED=false` by default. Disabled builds show no push settings, request no permissions and make no push API calls. Ordinary builds do not require Firebase or an EAS project.

## Backend contract, proposed and NOT deployed

Both endpoints below are **new contracts for the Backend team**, not existing production routes. The client handles their absence as an error. Leave rollout disabled until implementation and live integration testing are complete.

`PUT /notifications/push-devices` and `DELETE /notifications/push-devices`

Headers: existing Supabase `Authorization: Bearer ...`, `x-hardware-id`, `x-manga-dock-client: mobile`, and JSON content type.

```json
{
  "deviceId": "existing-native-device-id",
  "provider": "expo",
  "platform": "android",
  "token": "ExponentPushToken[example]"
}
```

PUT returns `200 {"registered":true}` **only after durable binding succeeds**. Derive the owner from verified Auth, never from a client-provided UID. Replace the current token for a device atomically; tokens must not remain bound to multiple recipients. DELETE is idempotent, owner-scoped and token-scoped, returning 204 even when absent. A late cleanup for one owner/token must not remove a newer binding.

Follow the existing Phase 5 architecture: PostgreSQL transactional outbox, a dedicated Redis notification queue, deduplication, bounded retries, dead letters and delivery receipts. Recheck ownership/preferences immediately before sending; expire inactive registrations and remove invalid tokens from receipts. Do not use the Cache Leader as a notification sender.

Expo message example, sent **server-side**:

```json
{
  "to": "ExponentPushToken[example]",
  "channelId": "mangadock-updates",
  "title": "MangaDock",
  "body": "มีความเคลื่อนไหวใหม่",
  "data": {
    "version": "1",
    "recipientUid": "verified-recipient-uid",
    "notificationId": "persisted-notification-id",
    "link": "/book/manga-id"
  }
}
```

Supported destinations are those already in `src/notification-links.ts`, including books, posts and profiles. New-chapter pushes currently open the book details; direct chapter/page routing and future collection routes require a separate agreed extension. Tapping a push does not mark the existing inbox notification read in this slice. Keep lock-screen text non-sensitive: background OS presentation cannot be filtered by the foreground JavaScript handler.

## Configuration and verification

Use an existing Firebase Android app for **`com.mangadock.mobile`**, its Android client config, and the existing EAS project UUID. Configure FCM v1 credentials in that EAS project for Expo Push Service, using the team's normal credential workflow. No cloud project was created or inspected in this implementation.

```dotenv
EXPO_PUBLIC_PUSH_ENABLED=true
EXPO_PUBLIC_EAS_PROJECT_ID=<existing-project-uuid>
GOOGLE_SERVICES_JSON=<local-or-EAS-file-path-to-google-services.json>
```

The build config rejects enabled builds without Firebase config or a valid project UUID. `google-services.json` is already ignored. Rebuild the native binary after installing the notification module/config plugin; an old APK cannot acquire it through a JavaScript reload. Use an Android device or emulator with Google Play services and a native development/internal build, not Expo Go.

Run from `Mobile/`:

```powershell
npm.cmd ci
npm.cmd test
npm.cmd run typecheck
npx.cmd --no-install expo prebuild --platform android --no-install
```

Source/controller/OS-boundary verification does not establish live push delivery or physical UI acceptance. Final verification results and build observations are recorded below before handoff.

### สัญญาที่ Backend ต้องทำต่อ

`PUT` และ `DELETE /notifications/push-devices` ตาม headers/body ตัวอย่างด้านบนเป็น **API ที่เสนอใหม่ ยังไม่มีใน production** ต้องคง flag ปิดจนทำและทดสอบร่วมกันแล้ว

PUT ต้องยืนยันเจ้าของจาก Auth บันทึกอย่างทนทานแล้วตอบ `{"registered":true}` เปลี่ยน token ของอุปกรณ์แบบ atomic และไม่ผูก token กับหลายผู้รับ DELETE ต้องทำซ้ำได้และจำกัดด้วยเจ้าของ/token เพื่อไม่ให้งาน cleanup เก่าลบทะเบียนใหม่

ฝั่งส่งใช้ PostgreSQL outbox กับ Redis notification queue แยกตาม roadmap มี dedup/retry/dead letter/receipts ตรวจเจ้าของและ preferences ก่อนส่ง กำหนดอายุทะเบียนและลบ token ใช้ไม่ได้จาก receipts ไม่ใช้ Cache Leader เป็นตัวส่ง

Payload Expo ตัวอย่างด้านบนส่งจาก server และต้องมี version/recipientUid/notificationId/link ลิงก์ตอนใหม่เปิดหน้ารายละเอียดเรื่องก่อน การเข้าตอน/หน้าโดยตรงและ Collections ต้องตกลง route เพิ่ม กด Push ยังไม่ทำเครื่องหมายอ่านใน inbox ในรอบนี้ ข้อความบน lock screen ควรไม่มีข้อมูลส่วนตัว เพราะ JavaScript กรองการแสดงของ OS ตอนอยู่เบื้องหลังไม่ได้

### ตั้งค่าและงานค้าง

ใช้ Firebase Android app เดิมที่ package `com.mangadock.mobile` และ EAS UUID เดิม ตั้ง FCM v1 credential ใน EAS ผ่านขั้นตอนทีม แล้วกำหนด env สามค่าด้านบน Build จะตรวจ Firebase config และรูปแบบ UUID เก็บ config ไว้ในไฟล์ที่ ignore อยู่แล้ว ต้อง rebuild Native binary หลังเพิ่ม module ไม่ใช่ reload APK เดิม และทดสอบบนเครื่องหรือ emulator ที่มี Google Play services ด้วย Native build ไม่ใช้ Expo Go รอบนี้ไม่ได้สร้าง/ตรวจ cloud project หรือเพิ่ม credentials จริง
