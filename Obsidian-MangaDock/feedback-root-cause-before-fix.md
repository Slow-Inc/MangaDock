# หา root cause จริงก่อน แล้วค่อยหาวิธีแก้

**กฎ:** ห้ามเดาสาเหตุ และ **ห้ามเสนอ/ลงมือวิธีแก้ก่อนที่ root cause จะถูกพิสูจน์ด้วยหลักฐานที่ *แยกแยะ* ระหว่างคำอธิบายที่แข่งกันได้** — user สั่งไว้ 2026-07-28 ให้ถือเป็น **พื้นฐาน** ไม่ใช่กฎเฉพาะงานใดงานหนึ่ง

## Why — วันที่สรุปสาเหตุผิด 2 เรื่องรวด

ทั้งสองเคสถูกโพสต์ลง GitHub issue ไปแล้วก่อนตรวจจริง และทั้งคู่เป็นการอนุมานที่ "เข้าเค้า" แต่ข้ามขั้นตอน:

**[#680] สรุปว่า "โค้ด render บน branch ให้ glyph advance ต่างจาก main"**
เหตุผลที่ใช้: *test เหมือนทุก byte + golden เหมือนทุก byte + ผลต่างกัน* → ดูแน่นหนา แต่ **ผิด**
ของจริง: `text_render.get_char_glyph` เป็น `@lru_cache(cdpt, font_size, direction)` ที่ **key ไม่มี font** และ `set_font()` เปลี่ยน global `FONT_SELECTION` โดยไม่ล้าง cache → หลังสลับฟอนต์ ได้ glyph (ทั้ง bitmap และ advance) ของฟอนต์เดิม · เป็น **บั๊ก production จริง และอยู่บน `main` ด้วย**
หลักฐานที่แยกแยะได้อยู่ในมือ **ตั้งแต่ต้น** แต่ไม่ตามต่อ: เทสต์ **รันเดี่ยวผ่าน แต่รันทั้ง suite fail** = order dependence ⇒ ชี้ shared state ไม่ใช่ความต่างของโค้ด

**[#679] เชื่อข้อความ fail ของเทสต์**
เทสต์บอกว่า *"driver ย้อนไปใช้ heuristic ≤4 ตัวอักษรก่อน #278"* → เอามาเขียน issue ตรง ๆ โดยไม่เปิด driver ดู → **ผิด**
ของจริง: driver มี provenance gate อยู่ (ของ landing: `sfx_merge.should_sfx_rescue` อ่าน `region.is_sfx`) แค่ **ชื่อฟังก์ชันต่าง**จากที่เทสต์ hard-code ไว้ · และถูกสลับ **โดยตั้งใจพร้อม benchmark** ใน commit `7e78341e` (เพราะ FP-drop ของ #278 ทำ SFX หลุดก่อน VLM rescue) — ไม่ใช่ regression และ **ไม่มี heuristic ≤4 ตัวอักษรอยู่ในไฟล์นั้นเลย**

## How to apply

1. **หลักฐานต้องแยกแยะสมมติฐาน** — "ผลต่างกัน" ไม่ได้บอกว่า *อะไร* ต่าง ออกแบบการทดลองที่ผลจะต่างกันตามสมมติฐาน (รันเดี่ยว vs รวม suite, สลับลำดับ, ตัดตัวแปรทีละตัว) ถ้าการทดลองให้ผลเดียวกันไม่ว่าสมมติฐานไหนถูก แปลว่ายังไม่ได้ทดสอบอะไร
2. **error / assert message ไม่ใช่ข้อเท็จจริง** — มันคือสิ่งที่คนเขียนเทสต์ *คิด* ว่าจะเกิด เปิดโค้ดจริงยืนยันทุกครั้ง เทสต์ที่ผูกกับ implementation (เช็คชื่อ symbol) จะกล่าวหาผิดเรื่องทันทีที่มีการเปลี่ยนทางเลือกอย่างตั้งใจ
3. **ต้องมี minimal repro ที่โชว์ *กลไก*** ก่อนเคลม — เช่น `advance 38 → set_font('') ยังได้ 38 → cache_clear() ได้ 32` พิสูจน์ว่า cache คืนของเก่า · แค่ "เทสต์แดง" ไม่ใช่ root cause
4. **เครื่องมือที่ได้ผลจริงในเคสนี้:** bisect ลำดับเทสต์ · diff ไฟล์ต้องสงสัยข้าม branch · `git log -S "<symbol>"` หา commit ต้นเหตุ แล้ว **อ่าน commit message** (ทำให้รู้ว่าเป็นการตัดสินใจที่ตั้งใจ ไม่ใช่ความผิดพลาด)
5. **แก้ก่อนรู้สาเหตุ = เสี่ยงกลบสาเหตุ** — เกือบเสนอให้ "เอา fix #541 กลับมาก่อน" ซึ่งจะแปลง mismatch เป็น **skip** แล้วบั๊กจริงหายจากสายตา (`main` ก็ถูกบังอยู่แล้ว: `635 passed, 4 skipped`)
6. **ไม่แน่ใจให้บอกว่าไม่แน่ใจ แล้วไปหาต่อ** ห้ามเสนอทางแก้คู่ขนานไปกับการเดา · และเมื่อรู้ว่าเคลมผิด **ถอนต่อสาธารณะทันที** (แก้/คอมเมนต์ใน issue) ไม่ปล่อยให้ข้อมูลผิดค้างไว้ให้คนอื่นใช้ต่อ
