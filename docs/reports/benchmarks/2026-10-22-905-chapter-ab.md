| arm | wall | per page |

| 9 x `POST /simple_execute/translate_patches` (serial) | 98.42 s | 10.94 s |

Structural parity: all 9 pages returned identical patch counts (10/7/4/5/5/8/6/1/5), region counts
(17/13/30/28/15/12/9/16/21) and page sizes — the batch path changes only the schedule.

## Environment caveat (why 1.16× and not 1.37×)

- Host CPU ran 45-100 % during the runs (desktop/agent load); the same in-process A/B measured **1.37×** on a
  quiet host (round 42) and 1.02-1.06× under load (round 54). CPU-bound phases (numpy/image ops, PNG encode) are
  what the GPU/gateway overlap cannot hide.
- A second full run on the same day **failed** on host commit exhaustion: numpy could not allocate 40 MiB
  (`(2560, 2048) int64`) with ~6 GB commit left system-wide. The batch path keeps **two page contexts** alive, so
  peak memory is higher than serial — a real operational tradeoff for memory-tight hosts.

## Decision

Stays **opt-in** (`MIT_BATCH_PIPELINE`, default off): it is faster with identical output, but the two tradeoffs
are (1) no live per-page progress events during the batch, and (2) higher peak memory. A quiet-machine run
(CPU <20 %, commit headroom) should confirm the 1.3-1.4× ceiling before anyone flips the default.
