# Post-render QA: read the Thai the page shows and compare it with what was intended

**Why.** The PRD's last quality loop is a post-render check: a Thai recogniser reads the rendered line and the
pipeline notices when the reader cannot. This round builds the offline half of it and calibrates it on real pages.

**What exists now**

- `manga_translator/render_qa.py` (pure, torch-free): NFC normalisation that keeps letters, digits and **combining
  marks** (a missing tone mark must still count) while dropping the spaces and punctuation the recogniser invents;
  Levenshtein CER; the suspicion rule (`CER >= 0.18` and at least 5 characters after normalisation).
- `MIT/tools/render_qa.py`: offline tool. `--page <jpg> --mit http://127.0.0.1:5003` POSTs the page to a running
  MIT, composes the returned patches exactly as the reader receives them, reads each Thai region back with
  `th_PP-OCRv5_mobile_rec`, and prints a CER table with the lines worth a human look (plus `--json`).
- `test/test_render_qa.py`: 7 tests, torch-free, run in the CI logic gate.

**Calibration on Haimiya ch. 6** (live MIT, current production stack):

| page | lines | median CER | flags at 0.18 |
|---|---|---|---|
| 2 | 1 | 0.105 | 0 |
| 9 | 7 | 0.000 | 0 |
| 10 | 4 | 0.135 | 2 |

Both flags on page 10 were checked by eye. One (`ถึงกับไม่ชอบความคิดนั้นขนาดนั้นเลยเหรอ~?`, CER 0.27) is a **clean
render** — the recogniser simply struggles with a dense four-line block, so the flag is a review candidate, not a
verdict. The other (`เธอเกลียด` read `เธอเก`) did not reproduce on the next render. Before the min-length guard,
the only alarms were four-character interjections (`ฟุฟุ` read `ฟพ`, `หืม?` read `หีม?`) — recogniser noise,
which is why lines under 5 characters are not flagged.

**Limits and why it is offline**
- Paddle sits in its own venv on this box (`C:/Users/xenod/venvs/paddle`) because `paddle2onnx`'s Windows DLL does
  not load, so no ONNX export; putting Paddle in the serving venv is not worth it. The tool is therefore a
  developer check, not an in-pipeline gate.
- The recogniser's own error floor is ~7 % CER on clean Thai, so the gate can screen but not certify; a human still
  confirms.
- One chapter, three pages.

**Path to an in-pipeline gate:** a working Thai ONNX recogniser (a native ONNX model, or a fixed `paddle2onnx` /
Paddle C++ build). The pure half — normalisation, CER, threshold, min length — is already in the repo and tested,
so wiring it later is a session call plus a telemetry field, not a redesign.
